Different, each with its reason:
- QEMU 6.2.0 (minimega container, Ubuntu jammy) vs 10.2.1 (shirudo-dev). No effect seen on boot, TPM or attest.
- -M virt,its=off: this repo's kvm wrapper turns off the GICv3 ITS for nested KVM on Apple vz. shirudo-dev boots
  with ITS on but needs the kvm-arm.vgic_v3_*_trap host kernel arguments instead.
- -drive if=virtio,cache=writeback (minimega) vs -device virtio-blk-pci (run.sh); seed.img read-write and
  format-probed as raw instead of readonly raw. The guest sees the same /dev/vda, /dev/vdb.
- No -virtfs shares (src, bundle, out, kernel, otel, oci). run.sh mounts them over SSH after each boot for its own
  tests; shirudo init does not use them. Upatches and evidence move over SSH (pass-check.sh --mm).
- minimega additions: -vnc, -qmp, -rtc clock=vm, USB xHCI + tablet + kbd, virtio-gpu, virtio-serial cc port,
  pci-bridge, empty cdrom, -S (start paused, minimega starts it), -net none, -uuid. None reach shirudo.
- -no-reboot, -display none, -monitor none (run.sh) are absent: minimega manages the process.

## Power-loss finding (2026-11-25)
A hard kill of QEMU (run.sh vm-stop, minimega vm kill) is a power loss for the target. The next boot completes, but
shirudo-initrd fails with "init: loading authenticated boot settings failed: Structure needs cleaning" (EUCLEAN from
the config activation checks): status "tampered" (ConfigActive ALERT, ChainIntact/TpmMeasured WARN, register not
bound), shirudo.service failed, and plain "systemctl poweroff" is refused ("active block inhibitor").
"systemctl poweroff --check-inhibitors=no", then a fresh boot (new swtpm process, same state), comes back "ok".
Seen 2 of 2 times after a hard kill; 0 of 2 after a clean poweroff. stage.sh and launch.sh down now power off
cleanly. Matters for OT: field devices lose power without warning.

## Power-loss finding, third case (2026-11-25, Task 4)
shirudo/down.sh's first version waited on a minimega query that errored (.filter on a column not in .columns), so
phenix exp stop killed rtu-s mid-shutdown (console ended at "chrony"). The next boot: rtu-s shirudo status tampered.
A clean down.sh (poweroff --check-inhibitors=no) and up.sh brought it back to ok. Totals: 3 of 3 hard kills -> next
boot tampered; 3 of 3 recovered by a clean poweroff and another boot.

## Power-loss root cause (2026-11-26, bead ww-hubl)
Not a shirudo bug: swtpm sends TPM2_Shutdown(SU_STATE) when QEMU disconnects, so the next Startup(CLEAR) is a TPM
restart (reset count unchanged) and shirudo sees the same TPM boot with its config PCR cleared (EUCLEAN). Killing
swtpm first, as a real power loss, gives an ok boot (spike/power-loss-e7.txt; docs/shirudo-evidence.md, Power loss).
